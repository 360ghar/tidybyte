# Growth & Marketing Assets

App Store marketing creatives for five surfaces, rendered in all 20 shipped
languages. Generated by `scripts/growth/`, validated by CI.

```bash
npm run growth          # render every asset for every language
npm run check:growth    # validate what is committed
npm run screenshots     # capture iPhone + iPad screenshots
npm run screenshots:duo # capture iPhone Duo screenshots (outer + inner displays)
```

The Duo run needs the device in a specific **pose** — `Closed` for the outer
display, `Open` (rotated to native portrait) for the inner. The script verifies
that before it captures and stops with the Device Hub steps if it is wrong; add
`-- --drive-devicehub` to let it click those controls for you.

## What exists

| Surface | Assets per language | Apple's limit |
|---|---|---|
| In-App Events | 3 events × (card + details) = 6 | 10 live, 15 approved |
| Custom Product Pages | 4 page creatives | 70 pages max |
| Asset Library | 2 creatives (header + search) | — |
| Product Page Optimization | 3 treatment creatives | 3 treatments + original |
| Header and Search | 2 creatives | — |

**357 images total** (17 assets × 21 languages) in
`docs/growth/<surface>/by-language/`.

## Why the art and the text are generated separately

Every asset is two layers:

1. **Background art** — generated with the `agnes-ai` skill. Text-free, brand
   palette, composed with a deliberate empty region on one side.
2. **Text** — rendered by Chromium from HTML/CSS, on top.

The split is forced by two facts that conflict. A diffusion model cannot render
20 scripts reliably — the Indic conjuncts and the Arabic joining forms come out
as mush. And Apple requires text inside a creative asset to be **localized for
every language the app supports**. Generating the art once and the type 21 times
is the only way to satisfy both.

The renderer is the same approach as `scripts/og-cards.mjs`: Playwright, an
inline HTML template, the Fredoka brand face. The difference is the font stack.

## Fonts are per-script, and that is not cosmetic

`public/assets/fonts/fredoka-var-latin.woff2` covers Latin only. For every other
script the stack names a macOS system face explicitly:

```js
hi: "'Kohinoor Devanagari', 'Devanagari Sangam MN', -apple-system, sans-serif",
ar: "'Geeza Pro', 'Al Bayan', -apple-system, sans-serif",
```

The generic `sans-serif` fallback picks a face with incomplete shaping for
several scripts, so conjuncts render as dotted circles instead of joined glyphs.
`FONT_STACKS` in `manifest.mjs` is the table; each entry was checked by rendering
a contact sheet and reading it.

## Text is never translated for marketing

Every string resolves from a source that already exists:

- `Tidybyte/Resources/Localizable.xcstrings` — the app's own UI wording
- `docs/appstore/listings.json` — the App Store listing fields

`manifest.mjs` holds the references; `resolveCopy()` resolves them per language.
A second, parallel translation of the same ideas would drift from the app, so
the asset says exactly what the screen behind it says.

To add copy that does not exist yet, add the key to the app's own catalog and
translate it there. Do not inline it in the manifest.

A key that is untranslated for a language renders in English and is reported by
`build-assets.mjs` rather than being skipped — a visible gap beats a missing
asset, as long as it is counted.

## Apple's accepted sizes

Verified against Apple's own documentation, not third-party summaries.

| Surface | Ratio | Accepted range | Rendered |
|---|---|---|---|
| In-App Event card | 16:9 | 1920×1080 – 3840×2160 | 1920×1080 |
| In-App Event details | 9:16 | 1080×1920 – 2160×3840 | 1080×1920 |
| Product page header | 21:9 | 3840×1646 exactly | 3840×1646 |
| Search results | 3:2 | 1920×1280 – 3840×2560 | 2400×1600 |

Also enforced: **no alpha channel**. App Store Connect rejects transparency, and
Playwright writes RGBA by default, so `omitBackground: false` plus a validator
check on the PNG color type is what keeps it out.

Apple allows text in a creative asset, but requires it localized for every
supported language. That is why coverage is a hard gate rather than a nice-to-have.

## Screenshots

`npm run screenshots` drives `xcrun simctl` to capture seven screens on both
required device classes:

| Device | Size | Requirement |
|---|---|---|
| iPhone 18 Pro | 1206×2622 | iPhone with Dynamic Island (medium display) — **required** |
| iPad Pro 13-inch (M5) | 2064×2752 | iPad 13-inch — **required**, because the app ships iPad |

Apple accepts 1179×2556 or 1206×2622 for the iPhone row, so 6.9" (1320×2868) is
**not** mandatory despite what `docs/APP_STORE_LISTING.md` used to say. Minimum 1
and maximum 10 screenshots per device size.

Two things the script has to do that are easy to miss:

- **Pre-approve the URL scheme.** `simctl openurl` raises SpringBoard's
  "Open in TidyByte?" dialog that blocks every navigation. Writing
  `com.apple.launchservices.schemeapproval.plist` on the booted device suppresses
  it. Writing it while the device is shut down has no effect.
- **Strip alpha.** `simctl` emits PNG color type 6 (RGBA); Apple rejects it. The
  script rewrites as color type 2.

Screenshots are captured in English only. Apple accepts a localized set per
language but does not require one — a localization without screenshots shows the
next best available language.

### iPhone Duo

`npm run screenshots:duo` captures the two iPhone Duo displays. It is a separate
run from the iPhone/iPad set and writes to two new directories:

| Display | Output | Size | Required pose | `--display` |
|---|---|---|---|---|
| Outer | `docs/screenshots/duo-outer/` | 1398×2034 | `Closed` | the UUID of the port whose size matches |
| Inner | `docs/screenshots/duo-inner/` | 2007×2853 | `Open`, rotated to native portrait | the UUID of the port whose size matches |

#### The pose: why the two displays need different ones

A Duo boots **folded**, and the two panels are never both showing the app:

- **`Closed`** — only the **outer** panel is active (1398×2034, showing the app).
  The inner panel is a live but empty surface; its screenshot is blank.
- **`Open`** — the app moves to the **inner** panel and the **outer** panel goes
  black.

So the two families cannot be captured in one pose. The inner panel also comes up
**landscape** (2853×2007) in the `Open` pose, and a portrait-only iPhone app then
renders letterboxed in a centred column; Device Hub's **`Rotate Right`** control
switches it to its native portrait 2007×2853, which is what a Duo capture needs.

Before capturing a family the script probes **both** panels, infers the pose from
which one has content, and compares it to the pose that family needs. If it does
not match, the run stops with the Device Hub steps that fix it and writes nothing:

```
✗ duoInner: the device is in the "Closed" pose, but iPhone Duo (inner display) needs "Open".
  observed: outer drawn (1398x2034), inner blank (2007x2853)

  Set the pose in Device Hub:
  1. Open Device Hub: Xcode > Open Developer Tool > Device Hub, or
       open /Applications/Xcode.app/Contents/Applications/DeviceHub.app
  2. Select "iPhone Duo" in the sidebar.
  3. In the device chrome, click the "Open" button (the poses group is Closed / Partially Open / Open).
  4. If the inner panel comes up landscape, click "Rotate Right" once to put it in native portrait.
  5. Wait for the panel to settle, then re-run this command.
  (Or re-run with --drive-devicehub to let the script click "Open" and "Rotate Right" for you.)

  Nothing was created or written for duoInner.
```

`simctl` has no hinge or pose verb and Device Hub has no CLI, so a pose cannot be
set from the shell. Two options:

- **By hand** — the default. The script prints the steps above and stops.
- **`--drive-devicehub`** — the script drives Device Hub through the `cua-driver`
  Accessibility CLI: it starts the daemon if needed, finds the Device Hub window
  for the target device (matched on the sidebar row's `TableRow.Device.<udid>`
  identifier, not on a name), locates the `Closed` / `Open` / `Rotate Right`
  button **by its AX label in a fresh snapshot** (element indices are invalidated
  by every snapshot, so none is ever cached), clicks it, waits, and then
  **re-verifies** through `simctl io enumerate` and a fresh pixel probe. A click
  that did not take is a failure, not a reason to capture anyway. If `cua-driver`
  is not installed the run stops and says so.

```sh
npm run screenshots:duo -- --drive-devicehub
```

#### The blank-panel gate

Every capture is analysed before it is accepted. A near-uniform image (all-black,
all-white, or effectively one colour) is rejected, and so is a wrong-size one,
with a message naming the likely cause — wrong pose, panel asleep, or the app not
frontmost:

```
  ✗ 99-blank.png  1398x2034 (blank panel (luminance 0-0, mean 0))
    → rejected: no app content drawn: wrong pose, panel asleep, or the app is not frontmost
```

This is the check that catches the black outer panel an `Open` pose produces: that
PNG is a perfectly valid 1398×2034 file, so a size-only check accepts it. The
statistics come from `pngjs`, already a devDependency and already imported for the
alpha strip; a hand-rolled decoder would mean re-implementing zlib inflate and the
scanline filters, and `sips` cannot report pixel statistics at all. `--check`
applies the same gate to files already on disk.

One Duo simulator serves both displays. `xcrun simctl io <udid> enumerate` does
**not** print `deviceName` or `screenID`; it prints `UUID`, `Class`,
`Display class`, `Default width`, `Default height`, `Default pixel format` per
port, and the ports include 720x480 and 7680x4320 decoys beside the real screen.
The script therefore selects by **pixel size** and passes that port's UUID. Audit
it on any booted device with `--probe <udid>`, which prints the table, the
inferred pose and the choice without capturing.

Port UUIDs change on every boot, so they are never cached across runs. The
documented fallback, used only when the dump yields no parsable display ports at
all, is the numeric screen id: `--display=1` is the outer 1398×2034 and
`--display=3` is the inner 2007×2853. Do **not** use
`simctl io screenConfig --display=<n> power off` — powering the outer panel back
on leaves it rendering black until the simulator is rebooted.

The seven screens, the settle times, the status-bar override and the alpha strip
are the same code the iPhone/iPad run uses.

Three things differ from the iPhone/iPad run:

- **It needs the iOS 27.1 runtime and the iPhone Duo device type.** Both are
  checked before anything is built, and if either is missing the script prints
  the `xcodebuild -downloadPlatform` and `simctl create` lines that fix it, then
  exits non-zero having created no device and written no file. A Duo device is
  always created on 27.1 — the device type declares that as its minimum.
- **It needs the right pose and orientation** (above). A family in the wrong pose
  stops before the output directory is created, so no partial set is left behind.
- **The size check is exact.** A Duo row is one fixed size, so a capture must be
  exactly 1398×2034 or 2007×2853; the 1179-vs-1206 slack the iPhone row allows
  does not apply. Every capture also has its PNG colour type read back to confirm
  the alpha channel is gone, not just that the strip ran.

`npm run screenshots:duo -- --dry-run` prints the whole plan — device, required
pose, orientation, resolved display, output path and expected pixel size — without
building or booting anything.

Apple's screenshot specification lists a **single** "iPhone Duo" entry carrying
all four sizes, and the Duo badge is described as one badge on the product page,
so these two directories feed **one** App Store Connect group by default: one
`APP_SCREENSHOT` row, both displays, one badge. The plan models it as one family
named `duo`; if the live catalog turns out to show two groups instead,
`publish:verify` is what settles it, and there is an escape hatch for that case.
The Duo screenshots are not uploaded by default — the group id is not known
offline. See `scripts/publish/README.md` → "iPhone Duo screenshots".

For checking how the app behaves across the foldable's poses and orientations
rather than capturing screenshots, use **Device Hub** in Xcode — the same app the
pose gate above tells you to click in.

## Adding an asset

1. Generate background art with `agnes-ai`, composed with an empty region.
2. Add an entry to the relevant surface in `manifest.mjs`, naming the art, the
   empty side (`left` / `right` / `top`), and the copy references.
3. `npm run growth -- --surface <id>`
4. Look at the output. The validator checks sizes and opacity, not taste.
5. `npm run check:growth`

## Things that are checked, and one that is not

`check-assets.mjs` fails on:

- dimensions outside Apple's range, or a wrong aspect ratio
- an alpha channel
- a missing language
- a blank or near-blank render, which is what a silently-failed background load
  produces (the file is a few KB instead of hundreds)

It does **not** check whether the text overlaps the art, whether a translation
overflows its column, or whether the result looks good. Those need eyes on the
output. Review a sample after any change to a font stack, a layout, or the art.
